企业级多模态数据中台 MVP（Lite 演示架构）— 系统部署开销评估报告

版本：v1.0（评审稿）　日期：2026-09-29 估算口径：方案阶段估算，用于立项与资源准备；实际以 POC 实测与采购时点报价为准。 架构说明：本版为演示优先的 Lite 架构——仅 4–5 个容器、唯一中间件 PostgreSQL，8GB 内存普通办公电脑即可全功能演示。 配套：01-详细设计文档.md、02-部署文档与演示指南.md

1. 场景划分

场景 用途 形态
S1 Lite 演示（本期交付） 售前演示、客户试用、开发自测 普通办公电脑，4 容器 Compose，整机 ≤ 8GB
S1-L Lite 演示 + 标注 需 Label Studio 专业标注台 5 容器，整机 ≤ 8GB
S2 部门试点（10–50 人） 真实业务轻量生产 一台 8C16G 服务器（同架构 + 定期备份 + HTTPS）
S3 规模化生产（50–300 人，非本期） 按演进路线拆分 多节点 + 对象存储 + 微服务/K8s

2. 硬件配置需求

2.1 Lite 版逐容器内存（稳态 RSS 估算）

容器 镜像基础 内存（稳态） CPU 磁盘（不含用户文件）
postgres:16 官方 300–500 MB 0.2 核 1–3 GB
platform-app（Java 单体，Xmx640m） eclipse-temurin:17-jre 700–900 MB 0.4 核 <300 MB
processing-app（FastAPI+pandas+Pillow+ffmpeg） python:3.11-slim 350–600 MB（视频转码瞬时 +300MB） 0.5 核（瞬时 1.5 核） <500 MB
portal-nginx nginx:alpine 20–40 MB <0.1 核 <100 MB
core 合计 约 1.4–2.1GB（上限按 2.5GB 设计） ≈1.2 核 约 2–4GB
label-studio（社区版，SQLite 库） 官方 600–1,000 MB 0.3 核 1–5 GB
core+label 合计 约 2.0–3.1GB（上限按 3.5GB 设计） ≈1.5 核 3–9 GB

加上 Docker Desktop/WSL2 与 Windows/macOS 自身开销（2–3GB），8GB 机器实测预期占用 5–6.5GB，留有 ≥1.5GB 余量，浏览器大屏与 IDE 也能同时开。

用户文件（raw+processed 双份 + 缩略图）按实际演示数据计；一次完整演示（含示例视频）< 500MB。建议预留 20GB 磁盘。

2.3 各场景推荐配置

场景 CPU 内存 磁盘 说明
S1 / S1-L 演示 4 核 8GB 20GB SSD 普通办公笔记本/台式机即可（i5/锐龙 5 近年代）
S2 试点生产 8 核 16GB 100GB 系统盘 + 数据盘（或挂对象存储） Java 堆可调到 2GB、worker 线程 4；每日备份
S3 高可用（路线） 3 节点 × 16C32G — 对象存储 + SSD 需按演进路线拆服务后再部署，非本期架构直接放大

容量粗算（S2 试点参考）：日均 1 万结构化文件 × 500KB + 200 多模态文件（图 3MB / 视频 50MB）≈ 15–20GB/天（双份）；文件建议直接挂载大容量盘或改对象存储，数据库年增长仅 10–30GB。

3.2 许可成本结论

  • Lite MVP 软件许可成本：0 元。
  • 唯一条件性费用：开发者电脑上的 Docker Desktop 订阅（达到条款门槛时），可零成本规避。
  • Label Studio 为 Apache-2.0（比 DataEase 的 GPL 更宽松），本期作为唯一可选外部系统。
  • 未来生产演进若引入 MinIO(AGPL)/Kafka(无影响)/DataEase(GPL) 等，保持"独立进程、网络集成、不改源码、不分发"即可，对外商业化前做一次开源合规审查。

6. Lite 架构的代价与风险（知情说明）

取舍点 演示期影响 生产期的补偿手段（已在架构预留）
Java 单体、Python 单实例 无；演示并发本来就低 按模块拆 3 个 Java 服务 + 网关；worker 先独立、多副本消费 PG 队列
PG 队列代替 Kafka 吞吐量上限约每秒数十任务，且轮询有 1–2s 延迟 量级上来后换 Kafka（JobQueue 接口已抽象）
磁盘卷代替对象存储 不能多机共享文件、无原生多副本 换 MinIO/S3/OSS（Storage 接口已抽象），配置项切换
进程内缓存代替 Redis 多实例后登录态/限流不共享 拆服务时引入 Redis
Label Studio 用 SQLite 单用户演示无影响；多人并发写性能弱 高并发标注时给 LS 挂 PostgreSQL（compose 改一行配置）
无 Nacos 配置中心 4 容器固定地址无影响 拆服务时引入
单 PG 节点 演示数据丢失可 down -v 重来 试点期每日逻辑备份；生产期云托管高可用或主从

结论：Lite 版牺牲的是"高并发/高可用上限"，保住的是"演示完整度 + 8GB 可跑 + 零许可费 + 极低运维"；且每一项取舍都在代码结构上预留了无重构演进路径。

7. 开销优化建议

  1. 演示一律 core 档（≤2.5GB），只在现场需要专业标注演示时提前 --profile label。
  2. 不需要现场跑 Label Studio 时，用门户内置手工标注入口演示闭环，内存最省。
  3. 8GB 机器若同时开 IDE/很多浏览器标签：JAVA_XMX=512m、WORKER_THREADS=1，容器内存可压到 ≈1.8GB。
  4. 视频样例控制在 20MB 内，转码瞬时内存几乎无感。
  5. 试点生产文件直接走大容量盘或云 OSS，避免为存储扩容整机规格。
